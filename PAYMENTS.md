# Shoein' — Payments & Invoicing

How farriers get paid through Shoein', and the roadmap for card payments.

## Where we are today (Tier 1 — shipped)

- The farrier saves **one payment link** (Venmo / PayPal / a Stripe Payment
  Link) on their profile — synced via the Firestore user doc
  (`businessName` / `paymentLink`).
- Invoices are generated on-device from a client's unpaid, priced visits →
  emailed as a PDF or texted as a summary, both including that link.
- The `paid` flag on each service record is flipped manually ("Mark paid").
- **No backend, no card processing** — Shoein' never touches money; the link
  just points the client at whatever the farrier set up.

**Limitation:** the amount is never enforced. The client types what they owe on
Venmo/Stripe. That's fine for trust-based, repeat-client work, but it isn't a
real "pay this exact invoice" experience.

---

## Why not a quick middle step (Tier 2)

We looked at making the pasted link Stripe-specific and passing the invoice
total in the URL. **Stripe intentionally does not allow setting the charge
amount via a query parameter** — a fixed Payment Link is bound to a fixed Price,
and there is no `?amount=` override (it would let anyone edit the URL and pay
$0.01). The only URL params allowed are non-money ones (`prefilled_email`,
`client_reference_id`, `locale`, promo code).

So the choices for getting the amount onto a Stripe page are:
- **"Customer chooses what to pay"** Payment Link — client still types the total
  (same trust model as today, just card-capable), or
- **Generate the link/invoice per-amount via the Stripe API** — the only way to
  lock an exact total, which requires a backend. That's Tier 3.

Tier 2 is only marginally better than what we already have, so we're **skipping
it** and treating Tier 3 as the real "payments" feature when the time comes.

---

## Tier 3 — Card payments with enforced amounts (planned)

Goal: an invoice opens a **Stripe-hosted page pre-loaded with the exact total**
("Pay $240"), the client pays by card, and the invoice **auto-marks paid** in the
app. Money goes **directly to the farrier**, not through an Auaha balance.

### Building blocks

1. **Stripe Connect (Standard accounts).**
   - Each farrier connects (or creates) **their own** Stripe account via a
     one-time onboarding link generated by our backend (Stripe hosts the KYC /
     bank-details flow — we never collect any of it).
   - We store only their **connected account id** (`acct_…`) on their user doc.
   - Standard accounts mean **Stripe handles all compliance** — KYC, payouts,
     1099s, disputes. Nothing touches our platform balance (direct charges on
     the connected account).

2. **A backend — Firebase Cloud Functions** (we're already on Firebase).
   - The Stripe **secret key lives only here**, never in the app.
   - Functions needed:
     - `createConnectOnboardingLink` — returns a Stripe Account Link URL for the
       farrier to finish onboarding; also a `createLoginLink` for their Stripe
       dashboard.
     - `createInvoicePaymentLink` — given an invoice (line items + total +
       client), creates either a **Stripe Invoice** (emails a hosted invoice
       with a Pay button) or a one-off **Payment Link / Checkout Session** for
       the exact amount **on the farrier's connected account** (`stripeAccount:
       acct_…`). Returns the hosted URL to drop into the SMS/email.
     - `stripeWebhook` — verifies the signature and listens for
       `checkout.session.completed` / `invoice.paid`; looks up our invoice by
       `client_reference_id` (or invoice metadata) and flips it to **paid**.

3. **App data model additions.**
   - `users/{uid}`: `stripeAccountId`, `stripeChargesEnabled` (from
     `account.updated` webhook so we know onboarding is finished).
   - A real **`invoices/{id}`** collection (today invoices are ephemeral):
     `{ clientId, lineItems, total, status: draft|sent|paid, stripePaymentLinkId,
     stripeSessionId, createdAt, paidAt }` — so the webhook has something to
     update and the farrier gets an invoice history.

### End-to-end flow

1. Farrier taps **Connect payments** in Profile → `createConnectOnboardingLink`
   → completes Stripe onboarding → `account.updated` sets
   `stripeChargesEnabled = true`.
2. Farrier builds an invoice (existing UI) → **Send** calls
   `createInvoicePaymentLink` → gets a hosted URL → sends via existing
   text/email path.
3. Client opens the link → pays the **exact total** by card on Stripe's page.
4. `stripeWebhook` receives `invoice.paid` → marks our invoice `paid` and flips
   the underlying service records' `paid` flags. The farrier sees it update live
   (Firestore stream).

### Money & fees
- Default: **direct charge** on the farrier's account; Stripe's fee
  (~2.9% + 30¢) comes out of their proceeds, deposited to their bank.
- Optional: add a small **`application_fee_amount`** on each charge as platform
  revenue (e.g. 0.5–1%). Adds a little complexity and a clearer value story for
  the subscription; can be deferred.

### App Store / Play compliance
- Farrier work is a **real-world service delivered outside the app**, so card
  payments via Stripe are allowed **without** Apple/Google IAP or their 30% cut
  (same category as Uber/DoorDash).
- **Keep the app's own subscription on RevenueCat/IAP** — do **not** move that to
  Stripe. The two never mix.

### Security notes
- Stripe **secret key** and webhook signing secret live only in Cloud Functions
  config — never in the client or the repo.
- The app only ever holds the **publishable** context (and doesn't even need
  that for the hosted-link flow) and the farrier's `acct_…` id.
- Verify every webhook with the signing secret before trusting it.

### Rough scope
- Firebase Cloud Functions project + Stripe SDK (one-time setup).
- 3–4 functions above + one webhook endpoint.
- Connect onboarding UI in Profile (a button + status chip).
- Promote invoices from ephemeral to a Firestore collection.
- Testing with Stripe test mode + a test connected account.

### Open decisions (for when we build it)
- **Stripe Invoices vs Payment Links / Checkout Sessions** — Invoices give a
  polished hosted invoice + automatic reminders + PDF (could replace our
  local PDF); Payment Links are lighter. Lean Invoices for the full experience.
- Whether to charge a platform application fee.
- Gate "card payments" behind the paid subscription (recommended — it's a strong
  Pro differentiator).
